### Gaps and risks, most serious first

1. **The signup path is broken at both ends.** The form exists only on the home page; the Table,
   the Trainer and every Learn guide (where search traffic lands) have no signup. In Beehiiv the
   welcome email is **off**, double opt-in is off, no postal address is set, reply-to is a personal
   Gmail and the sender is `mail.beehiiv.com`. The function asks Beehiiv to send a welcome email
   that does not exist, so a new subscriber gets silence until letter 001 ships. Attribution is a
   single `source` field that only ever says `home`; UTM parameters from a reel link are not kept.
2. **No safety net.** No `.github/`, no CI, no branch protection that I could see (the `gh` CLI is
   not installed, so protection could not be queried). Every push to `main` is a production
   deploy with no check. Tests cover `src/poker/` only; nothing exercises a page or the signup
   flow. Cloudflare Pages already builds a preview per branch and offers one-click rollback, so
   the missing pieces are checks and a rule, not infrastructure.
3. **Reels baseline drift.** The brief names v7 as the baseline. `main` is at v8 (commit c69009a,
   15:56 today), which changed four things at once (eases, decelerating counters, frame lift,
   vignette and grain), the pattern the brief forbids. The status lines in `content/reels/` still
   say "rendered (v4)". Reel 001 is a pre-library Higgsfield cut and is not in the two-round plan.
4. **Signup endpoint is open to scripts.** Browsers are blocked cross-origin (the preflight gets a
   405), but any script can POST addresses and pollute the list or burn Beehiiv quota. Only the
   honeypot stands in the way. No rate limit, no Turnstile. Also `reactivate_existing: false`
   means a returning unsubscriber sees "you're on the list" and is not re-added.
5. **Headers:** HSTS, nosniff, referrer and permissions policies are set. Missing:
   Content-Security-Policy and frame-ancestors (clickjacking). Low risk for a static site, cheap
   to add, must be tested against the Google Fonts and worker usage.
6. **Measurement is blind.** Visits are counted, but nothing says who ran the tool, answered a
   drill or signed up from which page. The brief's "do subscribers come back" cannot be answered
   without identifying people; the honest proxy is "visits that arrive from a letter link and then
   use the tool".
7. **Performance:** first paint at 2.2–3.5 s on mobile. Causes: the Google Fonts stylesheet blocks
   rendering, and one 282 kB bundle (90 kB gzipped) loads on every page including the text-only
   guides. Fixable in a day (self-host fonts with `font-display: swap`, split the tool bundle).
8. **Phone story.** Reels send phone traffic; the FAQ says the tool is "designed for a laptop or
   desktop". The phone pass made it work, but the landing experience for a reel viewer is unproven.
9. **Beehiiv trial ends in a week.** The pricing page says the free plan keeps API access (minus
   the Send API), so `/api/subscribe` should keep working; automations and a custom sending
   domain are paid. Verify on the plan page before day 14; do not pay yet.
10. **Dependencies:** 0 vulnerabilities in runtime dependencies, 12 in dev tooling (the vitest 2
    chain; `vitest@3` clears them). No Dependabot.
11. **Docs drift:** the brief references `docs/interface.md`, which does not exist; `content/README.md`
    references `content/calendar.md`, which does not exist; `docs/roadmap.md` numbering is broken;
    `docs/state.md` and `docs/decisions.md` did not exist (created this session).
12. **Social accounts:** `youtube.com/@llamapoker` is free (404). Instagram, TikTok, X and Threads
    return 200 whether or not the handle exists, so they are unverified.
13. **Legal footer:** no postal address or contact anywhere (CAN-SPAM needs an address in every
    email; Beehiiv may refuse to send without one). Privacy page is true today and must stay so.

What is fine: type-check, tests and build all pass; prerendering, canonical links, Open Graph,
JSON-LD, sitemap and robots are correct; www and http redirect with 301; trailing slash 308s to
the canonical; the 404 is a real 404 with `noindex`; runtime deps are clean.

## 2. Roadmap

I agree with the brief's shape: Phase 1 is publishing what exists. I split the first week out as
Phase 0 because the path has to be fixed before a single reel is posted, and it is two days of work.

### Phase 0: stop the leaks, then publish (days 1–7)

Builds: signup block on every guide, the Table and the Trainer result screen, with a per-page
source and UTM capture; Beehiiv welcome email (I draft, you approve), postal address, reply-to;
Turnstile plus a Cloudflare rate-limit rule on `/api/subscribe`; a `/go/<channel>` redirect per
social bio link so every channel is attributable; CI (type-check, tests, build) on pull requests
and `main`, branch protection, Dependabot, gitleaks, a documented rollback; reel voice round and
review-sheet round; letter 001 sent; social accounts created with the kit; reel status lines
and READMEs brought up to date.
Why now: reach is wasted while the path leaks, and every push is an untested deploy.
Effect on the north star: turns the first real visitors into the first real subscribers.
Cost: €0. Needs from you: approvals (welcome email, letter 001, reel rounds), account creation,
a postal address, the voice pick, the v7-or-v8 decision.

### Phase 1: publish on a rhythm and measure it (weeks 2–4)

Builds: the event store (one Analytics Engine dataset: page views with referrer and UTM, tool
runs, drill answers, signups with page and source, letter clicks); Privacy page updated; a weekly
growth review generated from the store, Beehiiv and a pasted Instagram export, written to
`docs/reviews/`; research agent v0 on official APIs only (Search Console, Reddit's public JSON,
YouTube Data) producing `content/research/<week>.md`; the first two new guides chosen from that
brief; the font and bundle performance fixes.
Cadence proposed (15 min/day plus one 90-minute batch on Sunday): two reels a week (Tuesday and
Friday, cross-posted to Shorts and TikTok the same day), one short letter a week, one guide every
two weeks, one hand-posted community answer a week as the distribution bet.
Why now: the cadence is the product; measurement makes each week teach something.
Effect: reach data and the first attribution. Cost: €0–10 (Cloudflare free tiers; no LLM calls yet).
Needs from you: a scoped Cloudflare API token, a Google service account for Search Console,
Instagram set to a Creator account, the Sunday batch.

### Phase 2: the engine behind the rhythm (weeks 5–8)

Builds: content drafts (guides, letters, reel scripts, captions) from the research brief using
`apps/web/src/poker/` numbers, via the Claude API; the approval queue as a Telegram bot backed by
D1 (approve, edit, reject from the phone), with scheduled publishing through official APIs
(Beehiiv first, then Instagram Graph and YouTube Data; TikTok stays manual until its API is
approved); pipeline logging into the same store; alerts; the global pause switch.
Why then: automation earns its place only after Phase 1 has published a few of each piece by hand.
Effect: holds the cadence without your evenings. Cost: €10–25/month in Claude API calls (about
20 drafts a month at Sonnet prices), everything else free. Needs: Anthropic key with a spend
cap, a Telegram bot, a Meta developer app and Facebook Page (Graph API requirement).

### Phase 3: experiments and the interface (weeks 9–13, only if traffic justifies)

Sequential before/after comparisons with a sample-size note on each; a read-only dashboard over
the event store; Agent-Reach or Osintgram only if a channel the official APIs cannot cover has
proven worth it. Hetzner stays unnecessary unless something must run longer than a Worker allows.

## 3. Targets

Assumptions: the reference account's first 15 posts got 1–4K views each and it broke out around
post 16; a new account posting two reels a week has 8 posts by day 30 and 24 by day 90; profile
visits convert to site visits at a few percent and site visits to signups at 1–3%; search grows
slowly from 3 indexed pages and 17 impressions.

| Horizon | Publishing | Reach | Subscribers (real people) | Confidence |
|---|---|---|---|---|
| 30 days (11 Dec) | 8 reels, 4 letters, 2 guides | 10K total reel views; 300 site visits excluding us; 200 search impressions | 25 | 50% on subscribers, 40% on reel views |
| 90 days (10 Feb) | 24 reels, 12 letters, 6 guides | one reel over 20K; 1,500 visits a month, 300 from search | 150 | 40% on subscribers, 30% on the 20K reel |

Quality check both horizons: at least a third of letter recipients click into the tool or a guide
within a week of a send. These are targets we can miss; a miss on reach with the cadence held
tells us the format or topics are wrong, a miss on subscribers with reach met tells us the path
or the offer is wrong.

## 4. Architecture and tools (one reason each)

- **Site:** stays React, Vite, Cloudflare Pages. It works and nothing here needs a server.
- **CI:** GitHub Actions running tsc, vitest and the build on PRs and `main`; Playwright smoke
  tests (home renders, table computes, guide renders, signup posts) against the Pages preview URL.
  Boring, free, native to the repo host.
- **Rollback:** Cloudflare Pages deployment rollback, documented in `docs/hosting.md`. Already
  exists; one click.
- **Spam and abuse:** Cloudflare Turnstile on the form plus a rate-limit rule. Free, no cookies,
  no CAPTCHA puzzles for humans.
- **Event store:** Cloudflare Workers Analytics Engine (events, SQL API) plus a D1 database (queue,
  pipeline runs, weekly aggregates). Free tiers cover us for years; everything later reads one
  store, which is what the brief's "built to grow" asks for.
- **Tracking beacon:** a 30-line first-party script posting to a Pages Function. No cookies, no
  IDs, no personal data, so no consent banner; the Privacy page says exactly this.
- **Schedulers:** Cloudflare Workers cron triggers. No server, same account, free.
- **Research:** Search Console API, Reddit public JSON, YouTube Data API. Official, free, no
  login to lose. Agent-Reach and Osintgram deferred to Phase 3.
- **Drafting:** Claude API, Sonnet 5.5 for drafts and Haiku 5.5 for triage, with a monthly cap.
- **Approval:** Telegram bot. Phone-native, free, done in a day; the interface replaces it later.
- **Publishing:** Beehiiv API, Instagram Graph API, YouTube Data API. Official only, per the brief.
- **Alerts and pause:** Telegram plus email; one KV flag every outbound job checks first.
- **Reels:** Remotion on the PC, frozen, batch sessions; renders uploaded to R2 for the queue.
- **Secrets:** Cloudflare and GitHub secrets; `credentials.json` stays local.
